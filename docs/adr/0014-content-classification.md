# 内容分类：feed 级主导 + 条目级 enclosure 覆盖，专属浏览形态

聚合内容按性质分流浏览：订阅源标注内容类型（文章/图片/视频/音频），文章级用 enclosure 信号做媒体覆盖；图片类源在单源页用画廊网格浏览。不引入社媒、通知两个独立类型。

## Status

accepted

## Context

RSS 世界没有「这条内容是什么」的可靠字段。需求是把内容按性质分流：图片看画廊、视频音频能一眼认出、文章维持现状。

代码事实（ADR-0014 立项时）：

- `ArticleEntity` 只有 `coverUrl`（解析时 enclosure 仅取 image 类型做封面），视频/音频信号在解析阶段就丢了。
- 纯 item 级自动判定的失败模式：RSS 的脏数据下（enclosure 缺失、MIME 胡填、正文与附件不符）逐条猜会大量误判，且每条都要持久化分类列；误判的卡片形态比没有形态更伤。
- 项目既有约束：不做双栏（正文排版长尾 + 性能顾虑）；媒体永不内嵌播放（CONTEXT.md「媒体占位卡」，ADR-0007 WebView JS 禁用的历史血案）。

## Decision

### 分类模型：两级信号

1. **Feed 级主导**（`feeds.contentType`：0=文章 / 1=图片 / 2=视频 / 3=音频）：
   - 订阅时用 `FeedContentTypeGuesser` 按地址与标题关键词预判（bilibili/youtube→视频、pixiv/instagram→图片、podcast/小宇宙→音频），只认高置信信号，猜不出就是文章。
   - 用户在订阅操作页可改。猜错不伤数据——改类型只影响列表形态。
   - 为什么 feed 级：订阅源几乎总是单一性质的（一个推特路由全是推文、一个播客路由全是音频），feed 级猜一次比逐条猜稳定。
2. **Item 级覆盖**（`articles.mediaKind`：0=跟随 feed / 1=视频 / 2=音频）：
   - 解析 enclosure MIME 与 media 模块的 type 前缀，video/audio 命中才写。图文源里偶尔夹一条播客或视频，feed 级解释不了它。
   - 列表卡片形态 = mediaKind 优先，否则 feed.contentType。

### 类型取舍：四类，不做的两类

- **社媒**：RSSHub 社媒路由产出的就是文章流，与文章的差异是展示密度而非内容本质 → 归入文章类。
- **通知**：RSS 语境里不存在独立的「通知内容」，追踪通知的 RSSHub 路由产出的就是文章 → 砍掉。

### 浏览形态：只改卡片，不改详情

- **文章类**：维持现状（**不做双列**——「双列」只适用于图片类视觉内容，正文排版长尾的旧约束不推翻）。
- **图片类**：单源页两列方图画廊（`ImageGalleryGrid`），标题压图；点击仍进详情。
- **视频/音频**：卡片缩略图角标（播放/音符）；无缩略图时显示类型 chip。点击进详情，媒体播放一律跳原站——遵守媒体占位卡词条，不碰 ADR-0007。
- 综合信息流保持单列卡片流，画廊只在单源列表页出现（混合流的网格会切碎时间线心智，与 ADR-0006 分页快照冲突）。

## Consequences

- DB v12 → v13：两个带默认值的 int 列，存量行零重写；`ARTICLE_LIST_COLUMNS` 同步加 `mediaKind`（OOM 防线）。
- 分类的正确性责任在「订阅时预判 + 用户可改」：预判错了用户改一次，不设自动纠错。
- 画廊无粘性日期头、无长按菜单（首期）；网格里没有它们的一席之地，后续有需求再议。
- 新增内容类型（如纯文本社媒紧凑卡）= 加一个 contentType 枚举值 + 一个列表形态分支，不动分类模型。

# 详情页正文渲染：混合模式（有图视口渲染，纯文字整页随滚）

文章详情页的正文 WebView 有两种布局模式，按正文里是否含 `<img` 动态选择：

- **整页模式**（纯文字正文）：标题 / AI 摘要卡 / 正文在同一个 Compose 滚动容器里，WebView 高度包内容、触摸穿透给外层滚动，头部随正文滚出视口（顶栏此时补位显示文章标题）。
- **视口模式**（正文含图）：头部固定，WebView 占满剩余空间、内部滚动、触摸归 WebView。

## Status

accepted

## Context

第一版详情页头部（源名 / 标题 / AI 摘要卡）固定在 WebView 之上，正文只占剩余空间，被反馈"固定头部占用大量空间"。随后改为"整页单滚动 + WebView 包内容高度 + `onTouchEvent` 返回 false 触摸穿透"，头部体验达成。

但整页包高有致命内存缺陷：Chromium 会把整页视为全部可见——一张数万逻辑像素高的页面里**所有图片同时解码进 Java 堆**，图多的文章在 256MB 堆上几十秒内 OOM。实测症状：停在阅读页不操作，"过一会儿"闪退；崩溃栈落在无关的数据库查询上（堆已满，任何分配都失败），具有强迷惑性。

## Considered Options

- **回退为视口渲染**（否决）：内存最稳，但完全放弃"头部随正文滚动"的体验。
- **保持整页渲染**（否决）：图多必崩。
- **CSS / lazy-loading 限制图片**（否决）：JS 已禁用，`loading="lazy"` 以 WebView 布局视口为界，包高模式下整页都在"视口内"，无效；CSS 缩放不减少解码内存。
- **混合模式（选）**：以 `contains("<img")` 判定。纯文字文章整页渲染内存可控（文字栅格可被 Chromium 回收），保住头部随滚体验；有图文章回退视口渲染，图片按视口解码。

## Consequences

- 有图文章的头部回到固定式，与纯文字文章行为不一致——为内存安全接受的取舍；顶栏补位标题在两种模式下都可用。
- 触摸行为按模式切换：整页模式 `onTouchEvent` 返回 false 穿透手势给外层滚动；视口模式 WebView 正常消费触摸。**整页模式下 WebView 内文字不可选中、链接不可点**（本来 JS 已禁用，外链统一走"查看原文"按钮）。
- 判定是启发式：`<img` 出现在注释/代码块里会误判为有图，代价只是少享受整页滚动，无害。

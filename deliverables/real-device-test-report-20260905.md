## 异常观察（0 崩溃，3 项待关注）

1. **手动刷新 3 分钟未结束**（20:00 触发，20:03 仍在转圈）：708 feeds ÷ Semaphore(8) × 最坏 50s 探测超时，理论可达数十分钟，属设计内行为，但 **无进度/剩余量反馈**，用户无法区分"在跑"与"卡死"。
2. **`A resource failed to call end` ×7**（20:00–20:02，伴随刷新）：Closeable 被 GC 回收而非显式关闭，疑似抓取路径 response body/input stream 泄漏。
3. **冷启动 Davey ×3**（821ms/762ms/1925ms 帧超时）：首帧组合阶段掉帧，中端机（Helio G96）上明显。

另：dropbox 显示 09-04 晚–09-05 早有 5 条 `data_app_crash`（contents lost，旧版 v1.0.1），本次会话 0 崩溃 0 ANR。MediaTek CtaUtils ClassNotFoundException 为小米 ROM 噪音，可忽略。

## 修复建议（按优先级）

1. **刷新进度可见化**：底部或顶栏显示「已抓取 n/708」计数（content_fetch_log 已有数据源），完成/失败时 Snackbar 汇总——符合"任何可能失败的交互必须让原因可见"铁律。
2. **排查资源未关闭**：刷新链路中 OkHttp `Response.body` / 输入流确认 use{} 包裹；可用 StrictMode `closeOnDetach` 或 LeakCanary 复核。
3. **冷启动优化**：首帧前避免同步读 DB 全量列表；考虑 splash 期间预热的分帧加载（Davey 1925ms 建议先量再来，别瞎猜瓶颈）。

# 代码审查：d739380「解析容错二次尝试 + 失效源刷新自愈」

范围：`core/data` 4 个文件（RefreshEngine / AppDatabase / RssParser / RssParserTest）
视角：正确性 → 并发安全 → 性能/内存 → 可维护性。已核对 ROME 2.1.0 `SyndFeedInput.build(Reader)`、
`XmlReader extends java.io.Reader`、`FeedProbeResult.from` 的 `IllegalArgumentException → InvalidFeed`
映射均成立（编译层面无误）。

## 做得对的地方

- 二次解析的分层判断是对的：严格解析优先，清洗只在失败路径付代价，健康源零额外开销。
- `updateUrl` 顺带清 `etag / lastModified` 是关键细节——旧 URL 的协商凭证带去新 URL 语义错误，
  命中 304 会丢整轮更新。内存副本同步置空也补上了。
- 自愈的降级契约清晰：「找不到返回 null、自身异常也返回 null」，不会把网络抖动放大成新问题。
- `findIdByUrl` 前置去重 + `articles.isEmpty()` 实解析校验，不会制造空壳源或重复源。
- 阈值走 `feed.consecutiveFailures + 1 >= 2`（用刷新前快照），与 FeedHealth 的失效判定对齐。

## P1（建议合入前处理）

### 1. `RssParser.parse` 全量 `readBytes()`，成功路径也要付内存代价

原来走流式 `XmlReader(input)`，现在每个 feed 都要完整落一份 `ByteArray`，失败时再产出一份
UTF-16 `String`（约 2× 字节数）。并发 32 路下峰值约 **3× feed 体积**；聚合源/播客源常见 5–10MB。
项目有 OOM 前史（ADR-0007 因 OOM 关掉 WebView JS），这里把单请求内存上限从「流式」抬到「整包」。

建议（二选一）：
- 加体积闸门 `MAX_FEED_BYTES`（如 12MB），超了直接 `IllegalArgumentException`（配合自愈正好）；
- 或保留流式首解析，失败时由调用方用可重放源重抓一次（RefreshEngine / SubscriptionFlow 都持有 URL）。

最低成本的一版：进 sanitize 前 `raw` 已无用，先置空/复用，避免 bytes 与 String 同时存活。

### 2. 自愈链路零测试

`tryHealUrl` + `healAndRefresh` 约 60 行网络 + 写库逻辑，一个用例都没有。测试缝现成的
（`RefreshEngineConditionalTest` 的 `Proxy` fake DAO + `HttpFetcher` 函参），补 3 个用例成本很低：

1. HTML 声明了可用 feed → `updateUrl` 被调用、补刷新成功、`recordRefreshSuccess` 落一次；
2. 候选地址已被订阅 → 跳过该候选，url 不变；
3. 全部候选失败 → 返回 false，url 与失败计数不变。

## P2

### 3. `sanitizeXml` 是 O(59·N) 且每次新建 `Regex`

59 个实体逐个 `t.replace(...)` = 59 趟全串扫描（命中就新建一份 String），末尾
`Regex("&(?!...)")` 又是**每次调用重新编译**。2MB 的坏 feed ≈ 上百 MB 瞬时分配。
改成单趟：预编译 `Regex("&([a-zA-Z][a-zA-Z0-9]{1,10};)")` + map 查表，控制字符过滤合并进同一个
`StringBuilder` 循环；`Regex` 与实体表放 `companion object`（现在是实例属性，每个 `RssParser` 一份）。

### 4. 大小写实体漏网：`&NBSP;` / `&AMP;` 修不了

实体名大小写敏感，HTML 里大写变体常见。查表前 `lowercase()` 一次即可
（注意 `&AMP;` 在 XML 里非法，应落到 `&#38;` 而不是放过）。

### 5. 自愈会在 `refreshAll` / 自动同步里放大耗时与流量

`healAndRefresh` 跑在 `refreshSemaphore.withPermit { }` 之内：单个坏源最多
1（抓 HTML）+ 8（候选校验）+ 1（补刷新）= 10 个请求，且最坏 10×20s 读超时**占着并发名额**。
700 源里若有 50 个坏源，全量刷新明显变慢，后台自动同步还会偷跑移动流量。

建议加每轮自愈配额（如最多 10 个源），或只在手动刷新 / `refreshSingle` 走自愈。

### 6. `tryHealUrl` 吞掉了 `CancellationException`

`catch (_: Exception)` 包住了 `feedDao.findIdByUrl` / `feedDao.updateUrl` 这两个**可取消的 Room
suspend 函数**（`http.fetch` 与 `parser.parse` 是阻塞调用，不抛）。结果是刷新被取消后仍会继续跑完
候选循环并写库。`healAndRefresh` 已经正确放行取消，这里保持一致即可：

```kotlin
} catch (e: CancellationException) { throw e
} catch (_: Exception) { return null }
```

### 7. HTML 硬解码 UTF-8，忽略 charset / BOM

`readBytes().toString(Charsets.UTF_8)`：GBK 中文站首页直接变乱码，autodiscovery 拿不到 href，
自愈对这类源等于失效。缝只给 `InputStream` 拿不到响应头，最省事的是把流直接交给 jsoup：
`Jsoup.parse(inputStream, null, baseUrl)`（jsoup 自己按 BOM / meta charset 探测）。

### 8. 静默改写订阅地址，无痕可查

自愈改掉 `feeds.url` 后：不通知、不留痕（`core/data` 无 Timber 依赖）。用户只会觉得「这个源内容变了」。
建议把自愈结果作为刷新结果的一部分回传（或写 `failureReason` / 单独一张记录），UI 至少能展示
「地址已自动修正」。

## P3

9. **缺同源校验**：候选与 `feed.url` 不同主机时也接受（站点声明指向 feedburner 之类）。
   建议加 host 校验，或对跨主机候选要求更严（条目数 / 标题相似度）。
10. `catch (first: Exception)` 变量未用，且第二次抛出时丢掉第一次的 cause；
    建议 `second.addSuppressed(first)`，排查「为什么清洗也没救回来」时省一轮。
11. 自愈改写后 `title` / `iconUrl` 不更新，旧文章仍挂在同一 `feedId` 下（不同源内容混杂）。
12. 非法字符范围偏窄：`isIllegalXmlChar` 只清 `<0x20` 与 `0x7F`，漏了 `0xFFFE/0xFFFF` 等 XML 非法码点。
13. 风格：`java.io.StringReader` 用全限定名而 `ByteArrayInputStream` 走 import；
    `HTML_ENTITY_REPLACEMENTS`（59 项）是实例属性，应在 `companion object`。
14. 测试只断言了 `title`，没覆盖 sanitize 的真实语义：`&amp;` 不被二次转义、控制字符被清除、
    大写实体。`sanitizeXml` / `isIllegalXmlChar` 已是 `internal`，直接写纯 JVM 用例更便宜。

## 建议的修复顺序

1（内存闸门）+ 2（补测试）→ 6（取消）+ 3（单趟清洗）→ 5（自愈配额）+ 7（charset）→ 9（同源校验）
